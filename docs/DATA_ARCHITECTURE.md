# 데이터 아키텍처: 현재 구현과 확장 설계

> 이 문서는 `main` 브랜치의 실제 코드 구조를 기준으로 작성한다. **구현**은 현재 코드에서 확인되는 동작, **부분 구현**은 작동하지만 범위나 연결이 제한된 기능, **미구현/제안**은 아직 코드에 없는 기능을 뜻한다.
>
> 최종 확인 기준: `SAVE_VERSION = 10`. 저장 형식과 데이터 필드를 변경할 때는 이 문서만 고치지 말고 실제 마이그레이션과 테스트도 함께 갱신한다.
>
> 사후 세계의 상세 설계는 [AFTERLIFE.md](AFTERLIFE.md)를 참고한다. 그 문서의 과거 저장 버전·선행 조건은 현재 코드와 다시 대조해야 한다.

## 1. 아키텍처 원칙

1. **플레이어와 NPC는 같은 인물 모델을 사용한다.** 플레이어는 별도 캐릭터 클래스가 아니라 `controller === "player"`인 NPC다.
2. **세계의 상태와 인물의 상태를 구분한다.** 세계에 남는 변화, 인물에게 귀속되는 소지품·기술·기억, 화면 세션 상태를 한 덩어리로 취급하지 않는다.
3. **세계에서 생긴 정의는 세계 데이터에 보존한다.** 세계에서 새로 생긴 직업·업무·종족·지식·아이템 정의는 `w.defs`에 저장한다.
4. **사건은 문장과 구조화 데이터를 함께 가진다.** 문장은 플레이어에게 보여 주는 서술이고, `data`는 후속 시스템이 사실을 읽을 수 있는 데이터다.
5. **새 기능은 기존 데이터 흐름과 연결한다.** 관계도·연대기·생애 사건 등 이미 존재하는 기능을 확인하고 중복 시스템을 만들지 않는다.
6. **미구현 설계를 구현된 것처럼 문서화하지 않는다.** 특히 창작물 보관·이전, 완전한 관계 유형, 사업체 소유권, 사후 세계는 별도 구분한다.

## 2. 런타임 구성

| 파일 | 책임 |
|---|---|
| `game/engine.js` | 세계·인물·시간·NPC 생활·직업·종족·관계 기초·경제·사건·저장/불러오기. `window.Asteria` 제공 |
| `game/content.js` 및 `game/pack-*.js` | 기본 콘텐츠와 콘텐츠 팩. `Asteria.extend(pack)`으로 정의 추가 |
| `game/game.js` | 지도·이동·아이템·인벤토리·건물·농사·업무 결과·플레이어 상태. `window.Game` 제공 |
| `game/sims.js` | 업무 시뮬레이터의 플레이어 조작 부품 등록 |
| `game/story.js` | 대화·미션·신문·에피소드·관계도 등 이야기 계층. `window.Story` 제공 |
| `game/ui.js` | 화면과 입력, 인물 기록 등 UI |
| `game/test.js` | 시나리오 기반 기능 테스트 |
| `game/render.js`, `game/art16.js`, `game/sprites16.js` | 월드 렌더링과 도트 에셋 |

### 모듈 의존성 및 주의점

- 엔진은 일부 지도·건물·아이템 관련 기능을 `root.Game`을 통해 호출한다.
- 게임 계층은 `Asteria`의 세계·인물·직업·기술 데이터를 사용한다.
- 이야기 계층은 엔진 사건·관계·기억을 이용하고, 엔진은 `onEvent`, `onLearn`, `onApproach` 등의 훅으로 상위 계층과 연결된다.
- 업무 시뮬레이터의 조작 부품은 `Game.registerHand` 및 `Asteria.TOOL_AUTO`와 연결된다.
- 엔진·게임·이야기 사이에 상호 참조가 있다. 신규 시스템을 추가할 때 이 의존을 더 넓히기보다 데이터와 좁은 인터페이스를 우선한다.

## 3. 세계 데이터 모델

### 3.1 World

세계는 `World` 인스턴스이며, 핵심 데이터는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `worldId` | 세계의 고유 식별자. `newWorld()`에서 생성하며 저장에도 포함 |
| `seed`, `rng.s` | 초기 시드와 난수 생성기 상태 |
| `name`, `day`, `clock` | 세계 이름, 날짜, 하루 안의 시간 |
| `towns` | 마을별 상태 |
| `nations` | 국가 정의와 국가별 메타데이터 |
| `founded` | 세계 안에서 새로 세운 마을 정의 |
| `npcs` | 인물 배열. 배열 인덱스가 인물 ID |
| `events` | 세계 사건 배열. 배열 인덱스가 사건 ID |
| `byChar` | 인물별 사건 ID 색인. 메모리에서 재구성하며 저장하지 않음 |
| `chronicle` | 중요 사건 ID 목록 |
| `assets` | 집 등 세계 자산 |
| `defs` | 해당 세계에서 발생한 콘텐츠 정의 |
| `war`, `weather`, `appts` 등 | 전쟁·날씨·약속 등 세계 진행 상태 |
| `land` | 세계 지형에 남는 플레이어 행동 흔적 |
| `session` | 화면·조작 상태 |
| `playerId` | 현재 플레이어로 조종하는 인물의 ID |

`byChar`는 영속 데이터가 아니다. 사건을 불러온 뒤 `reindexEvents()`가 행위자와 대상 인물 기준으로 색인을 다시 만든다.

### 3.2 마을과 국가

- `w.towns[id]`는 마을의 이름, 국가 ID, 인구 관련 설정, 식량, 물품 재고, 위치, 독립 상태 등을 가진다.
- `town.nation`은 국가 이름 문자열이 아니라 `w.nations`를 가리키는 ID다.
- `w.nations[id]`는 국가의 `id`, `name`, `since`, `founder`, `from` 등을 보관한다.
- 새 국가·마을은 세계 안에서 생성되며, 새 마을 정의는 `w.founded`에 보존된다.
- 콘텐츠에 정의된 기본 국가와 세계 안에서 생성된 국가는 같은 국가 참조 체계를 사용한다.

### 3.3 세계별 콘텐츠 정의

현재 `w.defs`는 세계에서 생긴 정의를 저장하는 영역이다. 기본 형태는 다음과 같다.

```js
w.defs = {
  jobs: [],
  works: [],
  knowledge: [],
  items: {},
  races: []
};
```

- 직업·업무·지식·종족은 정의 객체 배열, 아이템은 ID를 키로 하는 객체다.
- `applyDefs(w)`는 해당 세계의 정의를 콘텐츠 레지스트리에 반영하고 색인을 갱신한다.
- 저장된 세계를 불러올 때도 `w.defs`를 복원한다.
- v9 → v10 마이그레이션은 기본 콘텐츠 팩에서 제외된 도토리골 관련 정의가 기존 저장 세계에 필요하면 그 정의를 해당 세계의 `defs`로 옮겨 보존한다.

**중요한 제한:** 현재 `CONTENT`와 `JOBS`, `RACES` 등은 런타임 전역 레지스트리다. `applyDefs(w)`는 기존 생성 정의를 전역 배열에서 제거한 뒤 지정한 세계의 정의를 다시 올린다. 따라서 서로 다른 세계를 동시에 독립적으로 시뮬레이션하는 멀티월드 런타임은 아직 안전하게 분리되어 있지 않다. 세계별 정의를 저장하는 것과 여러 세계의 정의를 동시에 활성화하는 것은 별개의 문제다.

## 4. 인물 데이터 모델

### 4.1 공통 인물

플레이어와 NPC는 모두 `w.npcs[]`의 같은 인물 객체다. 주요 필드는 다음과 같다. 실제 생성 경로에 따라 선택 필드는 없을 수 있다.

| 영역 | 주요 필드 | 설명 |
|---|---|---|
| 정체성 | `id`, `name`, `race`, `heritage`, `culture`, `birthplace`, `identity`(미구현) | 인물 식별·종족·혈통·문화·출생지 |
| 외형·성장 | `look`, `age_days`, `grown`, `lifespan` | 저장된 외형, 나이, 성인 여부, 수명 |
| 사회·직업 | `job`, `side`, `town`, `home`, `house`, `controller`, `title`, `fame` | 직업·부업·거주·소속·사회적 상태 |
| 능력·상태 | `traits`, `skills`, `gold`, `health`, `hunger`, `energy`, `mood` 등 | 성향·기술·생존 및 생활 상태 |
| 관계 | `rel`, `parents`, `children`, `spouse`, `lover`, `goal`, `follows` | 호감도·가족·연인·목표·추종 |
| 생활·기억 | `mem`, `known`, `flags`, `dream`, `stat` 등 | 기억·소문·상태 표식·생활 관련 정보 |
| NPC 소지품 | `inv` | NPC가 실제로 소유한 물품 수량 |
| 플레이어 귀속 데이터 | `ext` | 해당 인물에게 귀속되는 플레이어 진행 데이터 |
| 생사 | `alive`, `death_day`, `death_cause` | 생존 상태와 사망 정보 |

위 표는 대표 필드의 영역별 안내이며, 모든 인물에게 모든 필드가 항상 존재한다는 뜻은 아니다.

### 4.2 종족·혈통·외형·성장

- `race`는 현재 인물의 종족 ID다.
- `heritage`는 혈통 비율 객체다. 혼혈 자녀는 부모의 혈통 비율을 절반씩 합산해 물려받는다.
- `look`은 피부·머리색·머리 모양·눈 색 등 실제 외형값을 인물 데이터에 저장한다. 자녀의 일부 외형은 부모에게서 유전된다.
- `birthplace`는 출생 당시 마을·국가·날짜 정보를 보관한다.
- `culture`는 성장 배경의 국가/문화 참조로 사용된다. 혈통이나 현재 국적과 같은 개념으로 취급하지 않는다.
- 종족 정의에는 `adultAge`, `lifespan`, `magic`, `traits`, `look` 등의 규칙이 들어갈 수 있다. 성인 판정은 공통 16세가 아니라 종족별 `adultAge`를 사용한다.
- 세계에서 종족이 생기거나 사라지는 생태계가 일부 구현되어 있다. 혼혈 종족의 생성, 환경·마력 변화 등은 코드의 생성 규칙에 따른다.
- **미구현:** 혈통·종족·문화와 별개로 인물이 스스로 규정하는 `identity`의 체계적인 모델.

### 4.3 기술과 숙련

- 인물의 지식과 숙련은 `n.skills[id]`에 통합되어 있다.
- 기술 항목은 기본적으로 `{ lv, xp }` 형태이며, 직업을 통해 배운 출처가 있는 경우 `from` 같은 부가 필드가 붙을 수 있다.
- `n.know`와 `ext.stats`를 별도 정본으로 사용하던 이전 구조는 v7 → v8 마이그레이션에서 `n.skills`로 통합됐다.
- 직업이 가르치는 지식은 전직 후에도 인물의 기술 데이터에 남는다.
- 지식 습득, 업무 수행, 반복 연습은 기술 경험치와 숙련도에 반영된다.
- 기술 정의 자체는 기본 콘텐츠 또는 세계별 `w.defs.knowledge`에 존재하고, 개인별 습득 상태는 `n.skills`에 존재한다.

## 5. 플레이어 상태의 저장 위치

게임 계층의 `Game.ext(w)`는 기존 UI·게임 코드가 사용하는 호환 창구다. 실제 값은 세 곳으로 분리되어 있다.

| 저장 위치 | 의미 | 예시 |
|---|---|---|
| `w.land` | 세계에 남는 지형·환경 변화 | 밭, 채집·벌목·유적 흔적, 지도 크기 정보 |
| `w.session` | 현재 화면과 조작에 한정된 상태 | 바라보는 방향, 이동 경로 |
| `w.player.ext` | 현재 플레이어 인물에게 귀속되는 진행 상태 | 인벤토리, 핫바, 도감, 미션, 수배, 약속·기록 등 |

- `Asteria.extStore`가 키별 저장 위치를 정하고, `Game.ext(w)`는 Proxy로 해당 위치에 접근시킨다.
- 현재 플레이어의 소지품은 `n.ext.inv`에 저장된다. NPC의 소지품은 별도 `n.inv`다.
- 플레이어가 다른 인물로 다시 태어나면 이전 인물의 `ext`는 이전 인물에게 남고 새 인물은 새 진행 데이터를 갖는다. 세계 지형에 남은 흔적은 세계에 남는다.
- `w.ext`는 저장 정본이 아니라 이 세 영역을 이어 주는 호환 접근 계층이다. 새 코드는 데이터의 실제 소유 위치를 직접 고려해야 한다.

## 6. NPC 생활·관계·경제

### 6.1 일상과 약속

- NPC의 시간별 행동은 `planHour()`, `liveHour()`, `lifeUntil()` 등의 흐름에서 계획·실행된다.
- 일, 식사, 휴식, 놀이, 친구 만나기, 장보기, 기도, 집안일 등 직업과 생활 상태에 따른 행동이 존재한다.
- 피로·허기·기분·날씨·성향·관계와 시간대가 행동 선택에 영향을 준다.
- 친구 사이의 약속은 날짜·시간·장소·활동을 갖고, 날씨나 축제 등 상황에 따라 조정될 수 있다. 약속을 지키지 못하면 관계에 영향을 줄 수 있다.
- 플레이어와 NPC의 약속은 게임 계층의 미션/일정 UI와 연결되는 경로가 있다.
- 이는 규칙 기반 생활 시뮬레이션이며, 모든 행동이 개별 서사나 복잡한 계획 AI로 처리되는 것은 아니다.

### 6.2 관계와 기억

- 기본 관계 값은 `n.rel[otherId]`의 호감도다. 가족은 `parents`, `children`, 배우자는 `spouse`, 연인은 `lover` 등 별도 필드로 연결한다.
- 관계도 시각화는 이미 `Story.relGraph()`와 UI의 관계도 화면에 구현되어 있다. 새 관계도 시스템을 중복 제작하지 않는다.
- 사건을 인물이 알게 되면 `n.mem`과 `n.known`을 통해 기억·소문이 축적되고, 기억은 감쇠하거나 다른 인물에게 전달될 수 있다.
- `Story.reasons()`는 현재 플레이어의 `journal`에서 특정 인물과 관련된 사건을 찾아 관계 변화의 단서를 보여 준다.
- **부분 구현:** 친구·경쟁자·스승·제자 등 관계의 성격을 독립적인 관계 유형으로 지속 관리하는 `relKind` 같은 축은 충분히 구현되어 있지 않다. 현재 관계도는 가족·연인 관계와 상호 호감도 중심이다.
- **미구현:** 관계 변화의 모든 원인을 인물별 구조화된 장기 기록으로 일관되게 보존하는 체계.

### 6.3 경제와 물품

- 마을 식량 경제와 노동·소득 흐름이 존재한다.
- `town.stock`은 마을별 물품 재고이며, 생산·업무 결과가 재고에 들어가고 주민이 구매·소비한다.
- 재고량에 따라 `stockPrice()`와 판매 가격이 달라진다. 빵·고기·음식류 등 일부 물품은 시간이 지나며 부패한다.
- NPC는 `n.inv`를 가지고 구매한 식량·약·도구 등을 보유하고 사용한다. 친밀한 관계에서 물품을 선물하는 행동도 있다.
- 재고 한도(어른 수)를 넘은 물건은 버려진다(`stockSupply()`, `t.glut`). 마을 사이로 저절로 옮겨지지 않는다.
- 장 보러 왔다가 못 산 것은 `t.missed`, 그것이 이어지면 `t.short{물건: 날수}`(`shortDay()`). 모자란 물건은 만드는 사람이 더 자주 만들고, 마을에 만드는 사람이 없으면 그 기술을 아는 주민이 부업(`n.side`)으로 거든다.
- **물류(구현):** 세계에서 생긴 직업 짐꾼(`job.haul = "goods"`)·마부(`"people"`)가 길 위를 실제로 오간다. 길 위의 일은 `w.trips[{id, by, kind, from, to, path, len, t0, t1, cargo, riders, back}]`, 사람은 `n.trip`을 가지며 그동안 마을 주민 수(`residents`)에서 빠진다. 경로는 마을 길 그래프의 최단 경로(`routeOf`), 자리는 `tripPoint`. 짐꾼은 남는 마을에서 사서 모자란 마을에 팔고, 마부는 기다리는 사람(`w.waiting`)을 태운다. 도착은 `arriveDue`.
- 짐꾼·마부는 도착할 때 떠나온 마을의 재고를 기억한다(`n.heard`). 플레이어가 아는 다른 마을의 재고는 `ext.stockSeen{마을: {day, stock, how}}`(가서 보거나 짐꾼·마부에게 들은 것)뿐이다.
- **부분 구현:** 물품 경제는 마을 재고·NPC 구매·소비까지 확장됐지만, 모든 생산자·상점·운송·가격 협상과 시장을 포괄하는 완전한 경제 시뮬레이션은 아니다.

## 7. 직업·업무·시뮬레이터

### 7.1 직업과 업무 데이터

- 직업 정의는 `CONTENT.jobs`에 존재하며, 기본 직업과 콘텐츠 팩의 직업, 세계에서 생긴 직업이 같은 정의 체계를 사용한다.
- 세계에서 새로 생긴 직업은 `w.defs.jobs`에 데이터로 보존된다.
- 업무 정의는 `CONTENT.works` 및 `w.defs.works`에 저장된다. 업무는 직업 ID, 수행 단계, 필요한 도구, 재료·결과물, 기술, 시뮬레이터 ID 등의 데이터로 구성될 수 있다.
- 지식과 사회적 수요에 따라 새로운 지식·직업·업무가 세계 안에서 발생하는 규칙이 일부 구현되어 있다.
- NPC의 직업 선택·전직과 업무 수행은 세계의 수요, 개인의 조건, 숙련 등을 참조한다.

### 7.2 플레이어 업무 실행

- `Game.SIMS`는 업무의 `sim` ID와 실제 처리 함수를 연결한다. 새 처리 방식은 `Game.registerSim(id, fn)`으로 등록한다.
- `Game.HANDS`는 `sims.js` 등에서 등록하는 플레이어 조작 구현이다. `Game.registerHand(id, impl)`로 등록한다.
- 엔진의 `Asteria.TOOL_AUTO`는 NPC나 자동 처리에 사용할 도구별 자동 모델을 제공한다.
- `workReady()`는 업무 처리 함수와 필요한 조작 부품/자동 모델이 준비되었는지 확인한다. `jobReady()`는 준비된 업무가 하나 이상 있는 직업인지 확인한다.
- 플레이어는 직접 조작하거나 자동 처리에 맡길 수 있고, 결과 품질은 조작 점수 또는 자동 판정으로 계산된다.
- **부분 구현:** 플레이어 업무는 공통 업무 정의와 등록된 시뮬레이터 부품을 조합하는 구조다. NPC 업무는 플레이어와 같은 미니게임을 직접 플레이하는 것이 아니라 수치 기반 처리 경로를 사용한다.
- **미구현:** 플레이어가 임의의 새 코드나 완전히 새로운 입력 방식을 직접 만들어 등록하는 범용 시뮬레이터 제작 기능. 현재는 개발자가 제공한 등록 함수와 조작 부품의 범위 안에서 확장한다.

## 8. 자산과 창작물

### 8.1 주거 자산

- `w.assets`는 현재 집 자산을 보관한다. 집 ID는 `house:<townId>:<houseNumber>` 형식이다.
- 집 데이터는 `kind`, `town`, `hid`, `owner`, `style`, `mods` 등을 가진다.
- 인물은 `n.house`로 거주하는 집을 참조한다.
- 출생 시 부모의 집, 결혼·이사 시 함께 살 집을 배정하는 규칙이 있다.
- 집주인이 사망하거나 떠나면 같은 집의 식구에게 소유권이 승계되는 경로가 구현되어 있다.
- 플레이어는 현재 주민 집 자산 대신 여관 방을 거처로 사용한다. 여관 꾸미기 데이터는 별도 경로에 남아 있다.
- **미구현/부분 구현:** 플레이어가 소유하는 주택·상점·사업체를 포괄하는 부동산·사업 자산 체계는 아직 완성되지 않았다.

### 8.2 창작물

- **미구현:** `w.designs`를 정본으로 하는 디자인 원본·제작자·버전·세계 귀속 시스템은 현재 코드에서 확인되지 않는다.
- 의상·장비·가구·건축·레시피·발명품 등 플레이어가 만든 창작물을 디자인 정의와 실제 제작된 물건으로 분리하는 구조도 아직 필요하다.
- 향후 창작 시스템은 세계 귀속, 창작자, 원본 디자인 ID, 버전, 실제 제작 수량·소유자를 구분해야 한다.
- 다른 세계로 디자인을 가져오는 기능이 추가되더라도 디자인 파일을 가져오는 것과 해당 세계에 완성품·역사·문화가 자동 생성되는 것은 구분해야 한다.

## 9. 사건·기억·연대기

### 9.1 사건 구조

`World.record(kind, text, options)`는 다음 핵심 값을 가진 사건을 만든다.

```js
{
  id,
  day,
  kind,
  text,
  actor,
  target,
  town,
  imp,
  sent,
  cause,
  secret,
  data
}
```

- `text`는 UI·신문·대화에 표시되는 서술이다.
- `data`는 사건의 사실을 구조화해 저장한다. 예: 직업 변경의 `{ from, to }`, 지식 발견의 `{ skill, how }`.
- `actor`와 `target`을 기준으로 `byChar` 색인에 사건 ID를 넣는다.
- `World.lifeOf(id, minImp)`는 인물별 색인을 이용해 해당 인물의 생애 사건을 조회한다.
- `cause`는 원인 사건을 가리켜 사건 사슬을 보존한다.
- 중요도 `imp >= 7`인 사건은 `chronicle`에도 들어간다.

### 9.2 저장과 사건 보존

- 저장할 때 모든 사건을 무조건 보존하지 않는다. 연대기·플레이어 저널·신문·에피소드·NPC 기억·목표가 참조하는 사건, 중요 사건, 최근 사건과 그 원인 사슬을 남긴다.
- 저장된 사건은 배열 형태로 압축되며, `data`가 있는 사건은 마지막 요소에 구조화 데이터를 추가한다.
- 불러올 때 사건 객체로 복원하고 인물별 색인을 다시 만든다.
- 따라서 사후 심판이나 영구 생애 기록이 모든 사건의 원본 보존을 전제로 해서는 안 된다. 장기적으로 반드시 필요한 사실은 별도 장부/요약 데이터로 보존하는 설계가 필요하다.

### 9.3 이미 존재하는 이야기 기능

- 중요 사건을 모은 `chronicle`, 아침 신문, 플레이어 저널, NPC 기억과 소문, 이야기 에피소드가 존재한다.
- 인물 기록을 확장할 때는 `World.lifeOf()`, 기존 관계도, 신문, 연대기 데이터를 우선 연결한다.
- 모든 사소한 행동을 영구 사건으로 남기기보다 기존 중요도·기억·저장 정리 규칙을 활용한다.

## 10. 사망과 사후 세계

### 현재 구현

- `World.die()`는 인물을 사망 처리하고 `alive`, `death_day`, `death_cause`를 갱신한다.
- 사망 사건을 기록하고 배우자의 사별 상태, 주변 인물의 애도, 집 자산 승계 등을 처리한다.
- 사망한 인물 객체는 `npcs[]`에서 제거되지 않는다.
- 현재 사망 원인은 `death_cause` 문자열과 사건 데이터에 남으며, 구조화된 영혼·심판 장부는 아직 없다.
- 사망 이후 UI의 다시 태어나기 흐름은 새 세계에서 시작하거나 기존 세계에 새 인물로 들어오는 경로를 제공한다. 관전 기능은 별도 UI/진행 모드이므로 사후 운명과 같은 개념으로 합치지 않는다.

### 설계 단계

- 사후 세계는 또 하나의 생활 시뮬레이션이 아니라 회고·심판·필요시 속죄·다음 운명 선택을 위한 중간 공간으로 설계한다.
- 심판은 단순 선악 점수보다 행위·의도·맥락·피해·반복성·영향·생전 책임 이행을 고려한다.
- 플레이어와 NPC는 같은 사후 규칙을 적용받되, 플레이어는 장면과 선택을 직접 경험하고 NPC는 규칙에 따라 처리한다.
- 구체적인 심판자, 기억의 범위, 속죄 방식, 환생·안식 조건 등 미정 사항은 확정된 구현 요구사항으로 기록하지 않는다.
- 구현 시 현재 저장 버전 v10을 기준으로 새 마이그레이션을 설계한다. 과거 초안의 v4 선행 조건을 그대로 적용하지 않는다.

## 11. 저장 형식과 마이그레이션

- 현재 `SAVE_VERSION`은 **10**이다.
- 저장 포맷 문자열은 `asteria-world`, 기존 저장 키 접두사는 `asteria.*`다. 호환성을 위해 임의로 이름을 바꾸지 않는다.
- `MIGRATIONS`는 이전 버전에서 다음 버전으로 순차 변환한다. `deserialize()`는 저장된 버전부터 현재 버전까지 마이그레이션을 적용한다.
- 현재까지의 주요 변경 흐름:
  - v2 → v3: 세계 ID 도입
  - v3 → v4: 국가 이름 참조를 국가 ID 기반 구조로 이전
  - v5 → v6: 플레이어 확장 데이터의 세계 지형/세션/인물 저장 위치 분리
  - v6 → v7: 혈통·외형·성인 표시·출생지·문화 데이터 도입
  - v7 → v8: 지식과 숙련 진행을 `n.skills`로 통합
  - v8 → v9: 마을 간 지도 간격 확장과 지형 기록 이전 준비
  - v9 → v10: 기본 팩에서 제외된 도토리골 관련 정의를 기존 세계의 `w.defs`로 보존
- 마이그레이션은 기존 저장의 의미를 보존해야 한다. 외형·나이·소지품·세계 귀속 콘텐츠가 이전 과정에서 갑자기 바뀌지 않는지 테스트한다.
- 새 필드를 추가할 때는 기본값, 옛 저장 변환, 저장/불러오기 왕복, 새 세계 생성, 기존 세계 이어하기를 함께 확인한다.

1. **문서 정합성 유지:** README의 테스트 시나리오 수와 통과 결과, DESIGN·AFTERLIFE의 저장 버전 및 기능 설명을 실제 코드와 맞춘다.
2. **세계 콘텐츠 컨텍스트 분리 검토:** 전역 `CONTENT`와 `applyDefs(w)`를 세계별 런타임 컨텍스트로 바꿀 필요가 있는지, 저장 슬롯 전환·관전·테스트 흐름을 포함해 설계한다. 단순히 `w.defs`가 존재한다는 이유만으로 멀티월드 격리가 완료됐다고 보지 않는다.
3. **관계 모델 구체화:** 현재 `n.rel` 및 가족 필드와 충돌하지 않도록 친구·경쟁·스승·제자 등 관계 유형과 변화 근거를 설계한다.
4. **창작물 모델 설계:** 세계 귀속 디자인 원본, 버전, 제작자, 실제 제작물·소유권을 구분한다.
5. **인물 기록 UI 확장:** 기존 관계도와 연대기, `World.lifeOf()`를 재사용해 인물 개요·직업·기술·자산·관계·생애를 연결한다.
6. **사후 세계 구현:** 사망 원인과 생애 사건에서 심판에 필요한 사실을 장기 보존할 데이터 모델을 먼저 설계한 뒤, 중간 공간과 플레이어/NPC 공통 판정을 구현한다.

각 단계는 코드 수정 전에 실제 의존 파일과 테스트 시나리오를 확인한다. 특히 저장 형식 변경은 반드시 마이그레이션을 동반한다.
